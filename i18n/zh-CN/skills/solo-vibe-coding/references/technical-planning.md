# 技术方案流程与输出结构

用于基于已确认需求生成技术方案。承接其验收条件与项目约束；未约定技术选择时，遵循[默认技术栈](architecture.md#默认技术栈)。

## 必选流程

必须依次执行以下三步，深度与任务规模相称；复用仍有效的结论，并核对当前适配性。

1. **使用 [search-first](https://github.com/affaan-m/ecc/blob/main/skills/search-first/SKILL.md) 调研。** 先查项目内相似实现、既有约定与可复用能力，再调查业界成熟方案、开源实现、组件或模板。按[通用复用要求](../SKILL.md#结合项目条件应用指导)核对，说明来源、覆盖、缺口及可直接复用、扩展或参考的部分。没有适用候选时，说明查找范围与原因。
2. **使用 [architecture](https://github.com/anthropics/knowledge-work-plugins/blob/main/engineering/skills/architecture/SKILL.md) 评估取舍。** 基于调研结果，比较适配性、复杂度、成本、扩展性、熟悉度、交付时间与维护负担，确定采用、适配、参考或自建的部分，说明理由、后果及剩余工作。选择明显时仍简述评估依据，无须强凑备选。
3. **使用 [system-design](https://github.com/anthropics/knowledge-work-plugins/blob/main/engineering/skills/system-design/SKILL.md) 展开设计。** 基于选定方向，按下述领域与三层结构形成可实施方案。结合现有系统交代改动与复用，以及必要接口、数据流、失败处理、容量、可靠性、假设与验证。新发现推翻取舍时，反馈到调研与评估后再确定设计。

在同一方案保留必要来源与取舍。方案任务交付设计与建议；安装、实现依任务授权。单独调研或评估的请求使用[架构指导中的对应入口](architecture.md)。

## 最终方案结构

横向按业务领域分治，明确各领域职责、边界与跨域契约；每个领域内部纵向按**数据结构 → 逻辑算法 → 控制算法**三层组织。

| 层次 | 说明什么 |
| --- | --- |
| 数据结构 | 数据的类型、表示、组织、关系与不变量；按需说明记录、数组、集合、链表、树等结构，以及内存与持久化表示。 |
| 逻辑算法 | 求解所需的知识、业务规则、关系、计算与正确性条件：输入与目标结果之间应成立什么。 |
| 控制算法 | 运用上述逻辑求解的策略：求值顺序、分支、迭代／递归与搜索；按需说明调度、并发、I/O 与失败恢复。 |

数据结构采用 Niklaus Wirth《[Algorithms + Data Structures = Programs](https://people.inf.ethz.ch/wirth/Books.pdf)》的含义，可参阅[作者公开修订版](https://people.inf.ethz.ch/wirth/AD.pdf)；逻辑与控制依据 Robert Kowalski《[Algorithm = Logic + Control](https://www.doc.ic.ac.uk/~rak/papers/algorithm%20=%20logic%20%2B%20control.pdf)》，区分“什么成立”与“如何求解”。领域分治与三层表达是本技能的方案组织约定，职责按项目约定映射到代码与运行边界。

方案按以下顺序呈现：

1. **总体方案与依据**：概括参考来源、复用与技术选择。
2. **逐个受影响领域展开**：交代职责，再依次给出数据结构、逻辑算法、控制算法。简单任务可以只有一个领域；未改层简述沿用的设计。
3. **跨域协作与实施验证**：通过接口和端到端流程串联各领域，逐项给出独立工作项的改动、验证、工作量、风险及依据、假设与未知。明确[真实验收](development.md#真实验收)场景，包括所需环境与代表性数据、用户操作、预期系统响应与结果、重要异常分支及必要证据。详略与需求规模相称，复用仍适用的已有场景。
