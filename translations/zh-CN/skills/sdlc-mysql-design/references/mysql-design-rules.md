## 数据建模

### 实体、关系与字段归属

- **R08a 记录粒度** 建模表时，定义每行代表的业务对象、关系或事件，保持同表记录粒度一致。 参见[示例](mysql-design-examples.md#记录粒度)。依据：P1。判据：每行均符合声明的业务含义。

- **R09a 关联与唯一性** 建模关系时，定义两侧的最少和最多关联记录数。 依据：P1。判据：两侧均有明确基数边界。

- **R09b** 建模一对多关系时，在多方保存引用。 依据：P1。判据：引用位于多方表。

- **R09c** 建模一对一关系时，通过引用列唯一约束限制至多一条匹配。 依据：P1。判据：引用列有唯一约束。

- **R09d** 建模多对多关系时，使用关联表。 依据：P1。判据：关联有独立承载表。

- **R09e** 同一对象组合可重复关联时，定义每次关联的业务含义、区分依据和唯一性范围。 参见[示例](mysql-design-examples.md#关联与唯一性)。依据：P1。判据：能区分合法重复关联与重复写入。

- **R10a 字段归属** 放置字段时，将其归入决定其值的对象、关系或事件，避免重复维护当前事实。 依据：P1。判据：字段放置符合值的归属，未重复维护当前事实。

- **R10b** 保存历史快照时，保留业务发生时的值，不随当前值更新。 参见[示例](mysql-design-examples.md#字段归属)。依据：P1。判据：更名或改价未重写历史快照。

- **R11a 引用完整性** 定义引用新增或变更时，明确目标是否必须存在及须满足的状态。 依据：P1。判据：存在性与允许状态均明确。

- **R11b** 定义目标删除或失效时，明确已有引用的处理方式。 依据：P1。判据：已有引用有明确处理结果。

- **R11c** 实施引用要求时，通过业务写入流程，遵守[键与约束](#键与约束)和[并发控制](#并发控制)。 参见[示例](mysql-design-examples.md#引用完整性)。依据：P1。判据：已提交写入保持声明的引用规则。

## 表结构设计

### 命名与注释

- **R12a** 命名数据库、表或字段时，使用小写字母、数字和下划线；禁止数字开头、保留字及含义未定义的缩写。 依据：P1。判据：名称满足字符、首字符及含义限制。

- **R13a** 命名索引时，体现列或用途；唯一和普通索引可使用 `uniq_`、`idx_` 前缀，主键索引名为 `PRIMARY`。 依据：P1。判据：名称体现用途，未将可选前缀变为强制。

- **R14a** 字段含义、状态值或约束变化时，同步更新字段注释及相关定义。 依据：P1。判据：注释与定义符合变更后的行为。

### 数据类型

- **R15a** 字段引用或比较相同值时，保持数据类型和符号属性兼容；存在兼容选项时，优先采用一致定义。 依据：P1。判据：引用或比较列的定义兼容。

- **R16a** 表示精确金额时，使用明确精度和小数位的 `DECIMAL`，或明确最小单位的整数。 依据：P1。判据：表结构定义了精确表示方式。

- **R16b** 定义金额值时，明确币种及舍入规则。 依据：P1。判据：币种及舍入规则无歧义。

- **R16c** 存储、传参或计算精确金额时，全程保持精确表示，禁止先用浮点数计算再转换。 依据：P1。判据：前序步骤未引入浮点舍入。

- **R17a** 定义 `FLOAT`、`DOUBLE` 或 `DECIMAL` 时，不设置已弃用的 `UNSIGNED`。 依据：P1。判据：这些类型未设置 `UNSIGNED`。

- **R18a** 定义是非字段时，采用 `is_xxx` 和 `TINYINT UNSIGNED`。 依据：P1。判据：名称和类型符合约定。

- **R18b** 写入是非值时，由应用校验取值为 0 或 1。 依据：P1。判据：其他取值被拒绝。

- **R19a** 使用 `CHAR` 时，核对尾随空格处理是否符合字段业务含义。 依据：P1。判据：对空格敏感的情形保留业务所需区别。

- **R20a** 选择或解释时间类型时，考虑 `TIMESTAMP` 在会话时区与 UTC 间转换，而 `DATETIME` 不做该自动转换。 依据：P1。判据：时间解释符合所选类型。

- **R20b** 需要保留原始时区名称或偏移时，另行存储。 依据：P1。判据：原始时区信息可恢复。

- **R21a** 定义审计字段时，以 `created_at` 记录创建、`updated_at` 记录最后修改。 依据：P1。判据：名称保持上述含义。

- **R21b** 审计可变业务记录时，设置两个审计字段；只追加记录仅设置创建时间。 依据：P1。判据：字段设置符合记录可变性。

- **R21c** 设计关联表等其他表时，按其审计需求决定审计字段设置。 依据：P1。判据：字段设置有审计需求依据。

- **R22a** 定义审计时间时，使用 `DATETIME(3)`、毫秒精度、北京时间及连接时区 `+08:00`。 依据：P1。判据：表结构精度与连接时区符合约定。

- **R23a** 定义审计字段默认值时，设置 `NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`，为 `updated_at` 另设 `ON UPDATE CURRENT_TIMESTAMP(3)`。 依据：P1。判据：DDL 包含对应子句。

- **R23b** 写入带审计字段的记录时，由数据库维护审计时间，应用不重复赋值。 依据：P1。判据：应用未重复设置审计值。

### 键与约束

- **R24a** 设计 InnoDB 表时，显式定义稳定、简短的主键。二级索引记录包含主键列，较宽主键会增加二级索引成本。 依据：P1。判据：主键已显式定义，并按二级索引成本评估宽度。

- **R25a** 字段必填时，设置 `NOT NULL`。 依据：P1。判据：必填列拒绝 `NULL`。

- **R26a** 定义约束时，禁止使用 `CHECK`。 依据：P1。判据：DDL 不含 `CHECK`。

- **R26b** 通过任一应用入口写入数据时，校验范围、枚举和字段组合，拒绝非法写入。 参见[示例](mysql-design-examples.md#应用层校验)。依据：P1。判据：各写入入口均落实校验。

- **R27a** 保障业务唯一性时，使用唯一索引，不以先查询再插入替代；考虑唯一索引允许多个 `NULL`。 依据：P1。判据：索引及可空性符合预期唯一性范围。

- **R28a** 定义幂等标识时，在业务操作和租户范围内保障唯一性。 依据：P1。判据：唯一键符合操作范围。

- **R28b** 定义参与幂等唯一性的列时，全部设置 `NOT NULL`。 依据：P1。判据：参与列均不可空。

- **R29a** 维护引用完整性时，禁止使用外键约束或级联；采用 R11c、R54a 的业务写入流程。 依据：P1, R11c, R54a。判据：DDL 无外键或级联。

### 字符集与排序规则

- **R30a** 存储文本时，采用 `utf8mb4`。 依据：P1。判据：文本定义采用 `utf8mb4`。

- **R31a** 文本列引用或比较相同值时，保持字符集及排序规则兼容；存在兼容选项时，优先采用一致定义。 依据：P1。判据：相关文本列定义兼容。

- **R32a** 修改排序规则时，先检查相等判断变化及新产生的违反唯一性的重复值。 依据：P1。判据：相等性与重复值检查先于修改。

## SQL 编程

- **R33a** 实现 SQL 业务流程时，禁止使用存储过程。 依据：P3。判据：流程不依赖存储过程。

- **R33b** 实现分支、提交或回滚时，由应用代码控制。 依据：P3。判据：这些决策由应用代码负责。

### 查询

- **R34a** 编写稳定业务查询时，显式选择所需列，避免 `SELECT *`。 依据：P3。判据：投影显式列出业务所需列。

- **R35a** 分页或单行选取需要确定顺序时，使用联合唯一确定行顺序的排序键。 依据：P3。判据：并列值不会造成顺序歧义。

- **R36a** 定义分页游标时，包含全部排序键。 依据：P3。判据：游标字段覆盖完整排序。

- **R36b** 评估游标分页一致性时，考虑并发修改排序键造成的遗漏或重复，不承诺跨页一致快照。 依据：P3。判据：一致性结论包含该边界。

### 数据修改

- **R37a** 数据错误应使写入失败时，不用 `INSERT IGNORE` 或 `UPDATE IGNORE` 掩盖。 依据：P3。判据：应失败的错误仍可见。

- **R38a** 构造 `UPDATE`、`DELETE` 时，防止空参数或动态条件遗漏导致全表操作；`LIMIT` 不能替代业务范围条件。 依据：P3。判据：空输入或缺失输入不会移除业务范围。

- **R39a** 按 R23a 解释 `updated_at` 时，将其视为随行内容变化自动更新的时间，而非每次更新语句的执行时间。 依据：P3, R23a。判据：未假定无内容变更的语句会推进时间戳。

- **R40a** 执行普通更新时，不用 `REPLACE INTO` 替代：主键或唯一键冲突可能使未提供字段恢复默认值并触发删除、插入行为。 依据：P3。判据：保留普通更新语义。

### 表达式与函数

- **R41a** 比较值时，保持类型匹配，不依赖隐式转换决定关键业务比较结果。 依据：P3。判据：比较操作数采用明确兼容类型。

- **R42a** 校验长度时，区分字节、字符和可见字形；`LENGTH` 计字节，`CHAR_LENGTH` 计字符，均不代表可见字形数。 依据：P3。判据：所选单位符合业务限制。

- **R43a** `NOT IN` 集合含 `NULL` 时，不将未匹配值可能得到的 `UNKNOWN` 解释为已确认不属于集合。 依据：P3。判据：含空值的情形保留三值逻辑。

- **R44a** 使用 `COUNT(DISTINCT ...)` 时，考虑其排除 `NULL`：单列形式排除空值，多列形式仅统计参与列均非空的组合。 依据：P3。判据：预期计数排除上述空值情形。

- **R45a** 解释 `SUM` 时，考虑空输入或全空值输入返回 `NULL`，以及 `GROUP BY` 未成组时无结果行。 依据：P3。判据：空输入、空值及无分组有各自预期结果。

- **R45b** 将空聚合替换为零时，仅在业务将其定义为零的前提下执行。 依据：P3。判据：补零有明确业务依据。

- **R46a** 定义连续时间区间时，优先使用左闭右开边界。 依据：P3。判据：相邻区间边界无重叠或遗漏。

- **R46b** 计算时间边界时，采用业务时区并与存储值使用一致时间基准。 依据：P3。判据：绑定参数与存储时间含义一致。

## 事务与一致性

### 事务管理

- **R47a 事务内语句限制** 准备显式事务时，在事务外完成查询、业务校验及写入准备。 依据：P2。判据：准备过程位于活动显式事务之外。

- **R47b** 执行显式事务时，仅允许必要数据修改及事务控制；禁止普通或锁定查询，以及写语句中的查询部分（包括子查询）。 参见[示例](mysql-design-examples.md#事务内语句限制)。依据：P2。判据：每条事务内语句均符合允许范围。

- **R48a 事务连接** 写入必须共同成功时，在同一连接的同一事务内执行；连接切换、异步执行及传播设置均须保持该边界。 参见[示例](mysql-design-examples.md#事务连接)。依据：P2。判据：全部必要写入共享连接和事务。

- **R49a 隐式提交** 执行业务写入时，不用 `START TRANSACTION` 模拟嵌套，也不在写入之间将 `autocommit` 从 0 改为 1；两者都会隐式提交。 依据：P2。判据：上述操作未拆开业务事务。

- **R49b** 执行业务写事务时，将 `ALTER TABLE`、`TRUNCATE TABLE` 等 DDL 排除在外。 参见[示例](mysql-design-examples.md#隐式提交)。依据：P2。判据：业务写入之间没有 DDL。

- **R50a 失败处理** 必要写入报错或不满足业务条件时，停止后续写入并回滚整个事务；单条失败不表示此前写入已撤销。 依据：P2。判据：此前必要写入未被单独提交。

- **R50b** 发生死锁或锁等待超时时，先确保完整回滚，再考虑重试。 依据：P2。判据：重试前无残留部分事务。

- **R50c** 在上述失败后重试时，仅在安全前提下重试整个事务，并设置有限重试次数。 依据：P2。判据：重试覆盖整个事务、有安全前提且次数有限。

- **R50d** 提交状态不明时，先按幂等标识核对结果。 参见[示例](mysql-design-examples.md#失败处理)。依据：P2。判据：恢复前先核对原操作。

- **R51a 外部操作边界** 业务流程包含外部调用或消息发送时，不将本地事务视为能与其原子提交或回滚。 参见[示例](mysql-design-examples.md#外部操作边界)。依据：P2。判据：本地原子性结论未涵盖外部结果。

### 并发控制

- **R52a 业务条件更新** 保护写入时，优先采用业务字段的写入时条件。 依据：P2。判据：写语句自身校验业务条件。

- **R52b** 依据事务外读取数据计算新值时，在写入条件中校验相关原值或有效版本，防止覆盖并发修改。 依据：P2。判据：过期计算无法静默覆盖并发修改。

- **R52c** 单条条件语句足够时，不额外开启显式事务。 参见[示例](mysql-design-examples.md#业务条件更新)。依据：P2。判据：足够完成操作的单条写入未额外加事务。

- **R53a 更新时间校验** 无合适业务字段时，仅在相关修改均改变 `updated_at` 且旧值在校验期间不会复用的前提下，匹配其原值。 依据：P2。判据：时间戳安全的两个条件均成立。

- **R53b** 使用时间戳校验时，在读写、序列化和绑定中完整保留毫秒。 依据：P2。判据：原毫秒值完整进入条件。

- **R53c** 无法保障时间戳安全条件时，采用不复用版本标识或其他并发机制。 参见[示例](mysql-design-examples.md#更新时间校验)。依据：P2。判据：未用不安全时间戳证明版本有效。

- **R54a 引用完整性** 引用新增或变更与目标删除或失效竞争时，按 R11c 使用条件更新、唯一约束及必要事务协调。 参见[示例](mysql-design-examples.md#客户引用的并发维护)。依据：P2, R11c。判据：并发提交结果保持引用要求。

- **R55a 更新结果判断** 判断必要写入是否成功时，先明确驱动返回匹配行数还是变更行数。 依据：P2。判据：结果解释符合驱动配置。

- **R55b** 写入条件未满足时，不判定成功；仅零变更行数不足以证明条件未满足。 参见[示例](mysql-design-examples.md#更新结果判断)。依据：P2。判据：区分无内容变化的匹配与条件未满足。

- **R56a 写入顺序** 事务竞争资源时，采用一致的表和记录写入顺序，不从 SQL 文本顺序推定实际锁顺序。 参见[示例](mysql-design-examples.md#写入顺序)。依据：P2。判据：竞争路径共享访问顺序，而不只是条件书写顺序。

## 数据库安全

- **R57a** 将应用数据传入 SQL 时，绑定值参数，不直接拼接。 依据：P3。判据：数据值使用驱动绑定。

- **R58a** 构造动态表名、列名或排序方向时，以代码白名单映射 SQL 结构，值占位符不能替代结构。 依据：P3。判据：结构选项仅来自允许的映射。

## 性能优化

- **R59a 请求往返** 优化业务操作时，在保持正确性和整体性能的前提下减少数据库请求。 依据：P4。判据：节省请求未削弱结果或恶化完整路径。

### 索引优化

- **R60a 索引复用与变更** 为主要查询设计索引时，优先在这些查询间复用。依据：P4。判据：索引选择考虑主要查询集合。

- **R60b** 既有路径满足性能需求时，不仅因新增 SQL 或条件增加索引。依据：P4。判据：新语法本身不足以成为新增索引成本的依据。

- **R60c** 合并或替换索引时，检查其他查询和唯一约束。 参见[示例](mysql-design-examples.md#索引复用与变更)。依据：P4。判据：既有访问需求和唯一性得到保留。

- **R61a 低区分度字段** 评估低区分度字段索引时，考虑目标分布、联合过滤、排序、覆盖、回表及写成本，不仅因不同值少而排除。 参见[示例](mysql-design-examples.md#低区分度字段)。依据：P4。判据：决策覆盖负载收益与成本。

- **R62a 前缀索引** 选择字符串前缀索引长度时，依据实际数据。 依据：P4。判据：长度选择有数据依据。

- **R62b** 保障完整值唯一性时，不用前缀唯一索引替代；它可能拒绝前缀相同而完整值不同的记录。 参见[示例](mysql-design-examples.md#前缀索引)。依据：P4。判据：合法完整值仍可区分。

- **R63a 联合索引** 排列联合索引列时，兼顾过滤、左前缀复用、排序和分组；等值列通常先于范围列，但不以区分度作为通用排序规则。 参见[示例](mysql-design-examples.md#联合索引)。依据：P4。判据：列顺序有查询模式依据。

- **R64a 排序成本** 评估 `filesort` 时，比较排序、扫描和新增索引维护成本，不仅因排序判定索引有误。 参见[示例](mysql-design-examples.md#排序成本)。依据：P4。判据：决策比较完整成本。

- **R65a 索引列与表达式** 按日筛选时间列时，优先直接使用时间范围条件。 依据：P4。判据：条件显式给出原列边界。

- **R65b** 必须按表达式筛选时，评估匹配的函数索引或生成列索引。 参见[示例](mysql-design-examples.md#索引列与表达式)。依据：P4。判据：候选方案匹配实际表达式。

- **R66a 前导通配符** 评估前导通配符搜索时，考虑普通 B-tree 索引通常无法为其提供有效范围扫描。 依据：P4。判据：未将索引扫描误认为有效范围定位。

- **R66b** 将搜索替换为全文或专门搜索时，保留原匹配语义。 参见[示例](mysql-design-examples.md#前导通配符)。依据：P4。判据：替换方案符合原业务约定。

### 查询优化

- **R67a 批量查询** 逐行查询可合并时，改用联表或批量读取。 依据：P4。判据：可合并操作不再逐行请求。

- **R67b** 确定查询批量时，按参数量、结果量和实际负载决定分组。 参见[示例](mysql-design-examples.md#批量查询)。依据：P4。判据：分组大小考虑这些资源维度。

- **R68a 数据库侧计算** 计算可用 SQL 准确表达且完整路径成本符合任务性能要求时，优先在数据库侧完成。 依据：P4。判据：计算位置满足任务的完整路径性能要求。

- **R68b** 更新计算值时，将计算及必要业务条件合入同一写语句。 参见[示例](mysql-design-examples.md#数据库侧计算)。依据：P4。判据：写入在计算时校验条件。

- **R69a 多路明细关联** 独立一对多关联用于汇总时，各明细集先按所需结果粒度聚合再关联，防止记录倍增和重复累计。 依据：P4。判据：各明细金额仅贡献一次。

- **R69b** 修正关联倍增时，不用 `SUM(DISTINCT ...)` 抵消。 参见[示例](mysql-design-examples.md#多路明细关联)。依据：P4。判据：相同但合法的金额未被合并。

- **R70a 联表分页** 按主记录分页并返回明细时，先落实完整筛选和排序再取页，明细相关条件也须先于分页，之后读取明细。 参见[示例](mysql-design-examples.md#联表分页)。依据：P4。判据：入选及排序条件均未推迟到分页之后。

- **R71a 大字段重复传输** 关联重复传输主记录大字段时，评估分别批量读取主记录和明细。 依据：P4。判据：比较包含传输及额外往返。

- **R71b** 拆分这些读取时，处理版本一致性并避免逐行查询。 参见[示例](mysql-design-examples.md#大字段重复传输)。依据：P4。判据：组装满足一致性约定且不退化为逐行请求。

- **R72a 大字段延后读取** 筛选、排序及分组不依赖大字段时，评估先处理标识及必要字段，再读取大字段。 依据：P4。判据：延后字段不是筛选前提。

- **R72b** 中间处理省略大字段时，保持去重和分组语义。 参见[示例](mysql-design-examples.md#大字段延后读取)。依据：P4。判据：结果保持原比较粒度。

### 写入优化

- **R73a 批量写入** 插入可合并时，优先使用多行 `INSERT ... VALUES`。 依据：P4。判据：可合并插入减少语句发送。

- **R73b** 更新可合并时，评估集合更新。 依据：P4。判据：评估保留条件和失败语义。

- **R73c** 选择写入批量时，按字段大小和实际负载验证。 依据：P4。判据：批量不只按行数决定。

- **R73d** 将事务拆为批次时，仅允许可独立提交的批次，保留必须共同成功的写入范围。 参见[批量写入](mysql-design-examples.md#批量写入); [原子更新](mysql-design-examples.md#原子自增减少往返并避免丢失更新)。依据：P4。判据：部分提交不违反成功条件。

### 执行计划与性能验证

#### 适用范围与判定

- **R74a** 无法凭表结构、索引和 SQL 可靠推断主要执行成本时，将语句归为复杂 SQL。 依据：P4。判据：静态分析对以下任一成本仍有实质不确定性：分布或参数影响的扫描、回表和索引选择；关联、子查询、聚合或去重的中间规模及执行次数；规模或字段大小决定的排序、传输或批量写入成本。

- **R74b** SQL 复杂时，要求专项性能验证；否则本技能不额外要求计划分析、性能数据集或压测。 依据：P4。判据：验证要求符合复杂性判定。

- **R76a** 判定 SQL 复杂性时，不单凭语句长度、联表数或返回行数。 参见[判定示例](mysql-design-examples.md#复杂-sql-判定)。依据：P4。判据：判定基于成本不确定性。

#### 验证方法

- **R77a** 执行专项性能验证时，使用目标版本及引擎的真实 MySQL，数据覆盖造成不确定性的规模、分布、参数和字段大小；空库或少量样例不足以替代。 依据：P4。判据：验证数据覆盖已识别的不确定性。

- **R78a** 为专项验证检查访问路径时，使用 `EXPLAIN`。 依据：P4。判据：访问路径有估算计划。

- **R78b** 需要实际行数、循环或耗时时，在评估执行成本及影响后，对支持的语句使用 `EXPLAIN ANALYZE`；它会实际执行语句。 参见[EXPLAIN 官方说明](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。依据：P4。判据：先检查支持情况及执行影响。

- **R79a** 执行专项性能测量时，测量实际请求及完整业务路径耗时，包含传输、读取和应用计算，不仅测首行或单条 SQL 时间。 依据：P4。判据：计时覆盖业务路径完成。

- **R79b** 增加负载验证时，仅对关键并发路径提出要求。 参见[验证过程示例](mysql-design-examples.md#依赖真实数据的验证过程)。依据：P4。判据：其他路径未被统一要求压测。

- **R80a** 报告性能验证时，说明条件、结果及未验证范围；使用索引、静态计划或小测试不能证明实际负载验证通过。 依据：P3。判据：结论未超出已执行证据。
