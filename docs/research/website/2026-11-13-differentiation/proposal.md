# 官网增量价值定位分析与方案

日期：2026-11-13。分析基线：`a3325f1bb36961c76e8e6221a9562e497b670c4a`。状态：研究与建议，尚未作为官网实施方案采用。

## 结论

官网需要说明用户已有 Agent 时，安装 Solo Vibe Coding 增加了什么，以及这种增加为什么值得安装和使用。建议定位为“给 AI 编程助手使用的、按任务组织的产品工作方法”：将专业指导选择、成熟方案复用、工程检查和项目约定组织到一个入口，帮助目标用户补齐自己不易完整提出的专业要求。

代码已能证明 Skill 明确写入了这些指导；尚无同等条件对照，不能证明它比直接使用 Agent 更快、更可靠或更少返工。下一步应先制作可归因的真实案例，再依据结果确定官网承诺和展示重点。

## 已确认诉求与当前差距

用户认可面向实际使用者的方向，但指出“随便拿一个 Agent 也能做出这个报价工具”，要求分析 Skill 的差别与价值，重新提出方案。原有受众继续成立：有制作目标，但没有完整技术判断力的人；项目维护知识库继续留在仓库维护区域。

当前首页的“把你想做的，变成能用的”和报价计算器说明了用途与可操作性。将产品名换成普通编程 Agent，这些表达仍大体成立。现有示例没有展示指导如何改变了工作，也没有比较安装前后，不能独立承担 Skill 增量价值的证明。

这不是已经证实“Skill 没价值”，而是产品特征、用户收益与比较证据之间尚未建立清晰连接。当前22项测试和公网核验证明官网工程行为，不能把这些结果自动归因于 Solo Vibe Coding；本仓库 AGENTS、宿主默认行为、其他指导和人工反馈都可能影响结果。

## 方法一：以真实替代方案确定定位

采用 April Dunford 的定位组件：替代方案、差异特征、特征带来的价值、最在意这些价值的人、产品类别。先回答客户为何选择，再组织页面叙事。[官方说明](https://www.aprildunford.com/post/storytelling-vs-positioning)

| 组件 | 对本项目的分析 |
| --- | --- |
| 首要替代方案 | 用户直接向同一个编程 Agent 提需求。这是用户本次明确提出的比较对象。长提示词和自行组合多个 Skill 是待用户访谈核对的其他替代方案。 |
| 可确认的特征 | 单入口按任务选择相关专业指导与资源；要求结合现有项目；优先复用；工程任务先建立合适检查；跨任务维护同一套项目约定。 |
| 价值假设 | 减少用户自行查找、组合、发现遗漏和反复提醒专业步骤的负担，帮助项目继续推进。尚未测量这些收益。 |
| 建议首批聚焦 | 在已确认受众中，优先服务愿意用 Agent 做项目、需要继续修改或交给别人使用、但不能完整提出专业工作要求的人。此为建议聚焦，不替代用户已确认的总体受众。 |
| 建议类别表达 | 面向 AI 编程助手的产品工作方法 Skill。解释它依附现有 Agent 工作，不塑造成另一个模型或独立制作平台。 |

一个能力强、得到充分提示的 Agent 也可能完成同样工作。项目现阶段可主张的是有源码依据的指导组织与使用方式，不能宣称这些方法独有，或保证每次调用都优于基础 Agent。

## 方法二：把特征连接到用户收益与证据

价值主张画布用于把产品提供的内容对应用户任务、阻碍与期望收益，避免仅列能力名称。[官方画布](https://www.strategyzer.com/library/the-value-proposition-canvas)

| 用户不易补齐的工作 | Skill 的明确指导 | 应展示的用户收益与证据 |
| --- | --- | --- |
| 不知道该找什么方法，也不会挑很多 Skill | 按任务取用专业指导与案例，读取原始指令及相关引用 | 展示一次真实任务采用了哪些相关指导、为什么适合，以及实际应用在哪里；证明任务组织方式，不以引用数量代替效果。 |
| 不知道该沿用什么、选什么现成方案 | 保留既有产品/品牌/技术约束，优先复用已有实现与合适成熟基础，并考虑许可、兼容与成本 | 展示符合本人项目条件的具体建议、取舍及实际实现；省时省钱需要另行测量。 |
| 不知道该检查什么才算完成 | 工程任务优先确定质量标准和自动检查，按实际执行报告交付状态 | 展示普通用户关心的行为是否实际通过、哪些还没验证；不用“测试条数多”代替可用性。 |

## 官网建议

### 核心表达

价值主张假设：把项目所需的专业要求组织成 Agent 可按任务取用的默认指导，减少用户自己补齐工作方法的负担。

建议首屏文案：

> 给你的 Agent，一套做产品的专业方法。
>
> Solo Vibe Coding 把需求、设计、开发与发布等任务的专业指导组织成一个 Skill，按当前任务取用。沿用你的项目与成熟方案，建立适合项目的检查，并保留后续修改需要的约定。

主按钮建议为“看看它如何推进一个真实项目”，次按钮为“加到我的 Agent 里”。此为待验证文案，不是已证明的提效承诺。

### 信息与视觉顺序

1. **先识别是什么、为何与自己有关。** 首屏明确它安装在现有 Agent 中，以及补充什么指导。右侧展示真实项目成果与三条短证据：“为什么这样选”“哪些行为已验证”“下一次修改保留了什么”；证据形成之前仅使用明确标注的说明性示意。
2. **用一个完整案例证明主张。** 同一项目呈现最初目标、重要选择、真实可用成果、检查结果与后续修改。用关键操作画面和短解释承接用户收益，来源与验证方式按需展开。
3. **解释具体增加了什么。** 用上表的用户语言说明方法选择、方案复用、检查与连续性。可比较实际观察到的有/无 Skill 结果，不预设普通 Agent 必然遗漏。
4. **再给场景和开始路径。** 保留做新东西、加功能、改善页面等目标入口及完整上手。报价工具保留为次级成果体验，保留既有URL，其本身不再承担差异证明。
5. **回答安装前疑虑。** “已有 Agent 还要加什么”“与长提示词或自己组合 Skill 有何不同”“需要哪些工具与费用”“哪些结果已经验证”。

沿用当前基础视觉与移动端能力。主要视觉从独立计算器转为带关键证据的真实案例；避免把专家类别、控制台、CI矩阵或维护文档变成首屏阅读任务。用户看到操作结果和相关理由，完整研究与维护材料仍在仓库。

SEO/GEO同步清楚定义产品类别、适用人群、增加的指导和实际证据；FAQ及案例页面围绕真实问题组织。案例正文预渲染，写清日期与验证范围；不以“最强”“全自动”或未经比较的提效数值塑造差别。

## 方法三：先验证价值假设，再扩大承诺

采用 Strategyzer Test Card 的假设、实验、测量和预先标准，避免把展示效果当成比较证据。[官方说明](https://www.strategyzer.com/library/validate-your-ideas-with-the-test-card)

### 首个对照案例建议

选择一个已有的小型收藏工具，两轮修改：先增加能用表格打开的导出、保持手机可用和原收藏操作；再增加“只导出当前筛选结果”。该场景适合观察现有项目复用、功能验收与连续修改。它不能单独代表全部设计、获客或生产部署能力；这些场景后续另行验证。

同一 Agent 和明确模型版本、相同工具权限/项目快照/业务需求/资源预算，使用独立干净会话和隔离项目。A组直接使用 Agent，B组额外安装并启用本 Skill；不给B额外的测试、文档或方法提醒。其他全局与项目指令保持一致，不把本维护仓库专用规则额外带给某一组；两组都可正常检索资料，不故意削弱A组。

第二轮分别开启全新会话，只承接各组自己第一轮留下的项目文件，提供相同的新需求；不把上一轮聊天或另一组结果放入上下文。B组按同样方式继续启用Skill。这样才能观察文件中项目约定的作用，而非把同会话聊天记忆当作跨任务连续性。

Skill与所读上游版本、模型、工具、日期和实际执行范围需要记录。可先安排三组配对运行作探索，报告每次结果；该规模不作为统计性优势证明。顺序交替并避免前一组输出进入后一组上下文。再以真实目标用户补充首用观察，区分业务确认和专业补救提示。

### 预先声明的测量与发布标准

- 主要观察：用户为补救遗漏而额外提出的专业提示次数；必要业务澄清单独记录，不以问得少作为好坏结论。
- 共同补救协议：在Agent声称完成或预定阶段预算到达时统一验收，根据同一事实答案表回应业务澄清。失败反馈分为“描述未通过的用户行为”“提醒补充专业工作方法”“提供具体实现指导”，分别计数；后两类计入专业补救提示。两组使用同一预先写定的失败反馈和升级规则，不因偏好的实现方法干预。运行前锁定每类反馈的次数、阶段预算及终止条件；可用的探索起点是每轮最多三次补救（一次行为反馈、一次方法提示、一次具体指导），到达总预算即停止并保留未通过结果。正式执行以前需按任务确定每级具体文本，不能由操作者临场为某一组加码。
- 共同质量底线：用户关键操作、中文及逗号/引号/换行等真实数据导出、手机操作、第二轮筛选范围，以及原收藏行为通过同一套事先确定的验收。验收依据实际需求，并由不知道组别的评审核对；不依据某一组生成的测试反向设置标准。
- 成本同时披露：总耗时、模型及工具用量、远程读取与安装准备成本。专业提示减少但耗时或费用增加时，报告取舍，不只展示有利指标。
- 比较判断：只有重复观察到专业补救负担降低、共同质量不退化，且成本符合用户事先约定预算，才考虑使用对应的有限收益表述。收益大小与预算接受范围必须在运行前确定并记录；本报告不预设未经用户研究支持的“提升百分比”。
- 结果接近时：如实把价值表述为方法组织、便于复用和统一约定，不宣称效果领先；发现回归则修复或收窄适用范围。若增加的安装和阅读成本没有带来目标用户认可的帮助，应调整 Skill 或目标场景。
- 公开材料展示业务需求、关键结果和验证范围；用单独的用户案例内容解释方法，不直接把维护档案或内部日志加入官网阅读路径。未实际启用 Skill 的现有工具不能追认为 Skill 效果案例。

### 官网信息效果验证

请目标用户看页面后，用自己的话说明：它加在什么工具上、比直接使用多提供什么、什么情况下值得安装，以及下一步怎么开始。记录原话与卡点；只有记住“能做工具”，仍说明信息没有完成任务。少量访谈用于发现问题，不宣称转化率已提高。

## 建议实施顺序与尚缺证据

先确定可验证主张与共同验收，完成首个真实对照与后续修改，再据结果制作案例和首页、同步双语/SEO。继续保留现有用户场景、安装路径、轻量静态托管与维护入口边界。

尚缺：Skill可归因的完整案例、同等条件对照、真实目标用户理解与使用观察、成本收益接受度及真实搜索表现。官网信息设计可以提出假设，不能弥补产品本身若未产生增益的缺口。本轮仅研究与形成建议，官网与两个 Skill 包的行为未修改。
